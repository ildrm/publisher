## Contract baseline and consumers

[OpenAPI](../contracts/openapi.yaml) uses OpenAPI 3.1.1 and its JSON Schema dialect based on 2020-12, a deliberate proposed compatibility target rather than claiming to be the latest version; latest official versions are tracked in the standards register. [AsyncAPI](../contracts/asyncapi.yaml) uses 3.0.0. Files use JSON syntax, which is a valid YAML subset. These are representative pilot contracts, not every full-universe endpoint. The coverage extension records operations that still need domain-specific specification. Local checks parse JSON, resolve local references and validate explicit structural rules; full standards-conformance validation remains a release gate until the appropriate validators are installed.

## HTTP behavior

Bearer authentication identifies the user; server-side resource policy and current access epoch authorize every operation. Cookies, if used by the web adapter, require CSRF controls and secure SameSite session policy. Public catalog is explicitly unauthenticated; private requests never accept tenant scope solely from a client body. UUID identifiers do not prevent IDOR. Pagination uses opaque signed cursors, page limit 1–100 and deterministic `(created_at,id)` order. Private response caching is `no-store`.

For mutation commands `Idempotency-Key` is 16–128 characters, scoped to actor, operation and resource, stored with request hash and result. Authenticate and check current resource authorization before disclosing a stored receipt: a revoked actor receives denial even if their earlier mutation committed. Once authorized, same key/different body yields 409; same key/same body yields the original result even after current revision advances, before evaluating a stale base. Proposed receipt retention is 7 days; longer provider-event and financial uniqueness is permanent within legal retention. After the API receipt expires, a client with an uncertain outcome must reconcile against the authoritative resource before initiating a new command; a replay guarantee cannot be assumed beyond the receipt window. This 7-day API window is a design assumption for architecture review. `If-Match` uses the quoted revision UUID; stale writes return 412 with latest version ID but no unauthorized content. Auth 401, scope 403 (or uniform 404 where enumeration is sensitive), validation 422, rate limit 429 plus Retry-After, conversion failure 409/422 typed detail, and temporary 503 are distinct. Problem responses omit stack traces and private text.

Proposed pilot ceilings: 60 saves/minute/project/session with a burst of 20, 5 conversion submissions/minute/account, and 120 public catalog reads/minute/IP. These are configuration hypotheses, not measured capacity or contract limits. Responses include correlation IDs and accessible user-action messages. Upload initiation and completion are separate; download tokens are short-lived (proposed 60 seconds), bound to user/artifact and rechecked at redemption. A previously delivered offline file cannot be erased by revocation.

## Versioned events and consistency

The envelope has UUID event ID, schema version, event type, tenant/resource IDs, per-aggregate sequence, occurred-at timestamp and correlation ID. Payloads contain references, not manuscript text or card details. Outbox commits with the business transaction; dispatcher retries with bounded exponential backoff and jitter. Consumer inbox uses `(consumer,event_id)` uniqueness; poison messages move to DLQ after a configurable attempt budget (proposed 5). Per-aggregate sequence gates out-of-order processing; gaps trigger replay/reconciliation rather than silent discard. The supplied RevisionSaved v1 schema is closed: adding payload/envelope fields, removing/renaming fields or changing semantics creates v2 with an overlap/upcasting period. Consumers explicitly select supported versions; they must quarantine unknown versions rather than misparse them. If a future schema deliberately allows an extension object, only that object may accept optional additions without a new version. Event schemas and [example payload](../contracts/schemas/revision-saved.v1.json) are versioned.

Webhook endpoint uses raw-body signature verification, timestamp/replay window and provider account verification before parsing effects. Valid signed callbacks can still be duplicated or stale. Store a minimal inbox record, query provider state if ambiguous, and acknowledge only after durable intake. API authentication must not be accidentally bypassed because the provider uses signatures rather than user JWTs.
