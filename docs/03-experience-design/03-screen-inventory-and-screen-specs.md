## Shared contract for every screen

Each row below extends these defaults: structure is heading → context → primary content → primary action → secondary action; global and scoped navigation precede content and a skip link precedes navigation. Keyboard focus follows visual order; each control has an accessible name; errors identify the field and move focus to an error summary, while asynchronous completion is announced without moving focus. Desktop has two columns where useful; narrow layouts stack and avoid horizontal scrolling, except a separately scrollable content area when necessary. Use the semantic tokens in [design tokens](04-design-system-and-design-tokens.md). Loading announces “Loading…”; empty state describes the next permitted action; error explains recovery; success announces the completed result. Disabled actions explain why without relying on color. Confirm irreversible deletes, revocation, release, refund and payout in a dialog that names the target, consequence, cancel and confirm action; restore focus on cancel. Server authorization and validations are authoritative. Telemetry captures screen ID, outcome and duration only after consent/policy; never capture private prose, credentials or payment details.

Acceptance for all rows: given unauthorized access, direct navigation returns a safe denial without sensitive data; given keyboard-only use, the user can reach all available controls in order; given an operation fails, the prior committed data is preserved and a recovery action is provided. Responsive, screen-reader, RTL, validation and failure checks are required before approval; these are design contracts, not tested implementation.

## Requirement-family key

The table’s `IAM`, `DOC`, `IMP`, `EXP`, `PUB`, `RGT`, `FMT`, `3D`, `CAT`, `COM`, `FIN`, and `OPS` abbreviations refer respectively to FR-IAM-001–002, FR-DOC-001–003, FR-IMP-001, FR-EXP-001, FR-PUB-001–002, FR-RGT-001, FR-FMT-001, FR-3D-001, FR-CAT-001, FR-COM-001, FR-FIN-001, and FR-OPS-001. They identify related capability families rather than asserting complete one-to-one requirement coverage. P1 screens lacking an atomic FR need catalog decomposition and test IDs before implementation.

## State, validation and data boundaries

SCR-007 exposes “Saving…”, “Saved”, “Changes not saved” and “A newer version exists” independently of chapter navigation; a save response includes revision identity. SCR-012 limits uploads by configured type and size, scans before processing, shows warnings before confirmation and issues time-limited scoped downloads. SCR-016 validates declarations; SCR-020/023 show approval versions and block stale artifacts; SCR-021 validates grant interval and scope without interpreting copyright ownership; SCR-027 uses provider-controlled payment fields and a pending state to prevent repeat payment; SCR-032 displays currency and reviewed balance and requires a separate approver. SCR-034 requires explicit scope and expiry and asks confirmation before revocation.

P1 screens must not be presented as released functionality. Routes and example labels are provisional until prototype and contract review. Concrete pilot validation contracts below supplement the shared states; real usability evidence and full P1 field specifications remain open.

## Critical pilot screen validation contracts

All text below is proposed copy. Input limits are configured values until tested and agreed; the server rejects oversized or invalid input rather than silently truncating it. Each screen keeps entered data on validation failure where safe and returns focus to the first error, with a screen-reader error summary. Actions operate on the displayed version; a stale version requires reload and review.
